# Testing

## Stack

- **xUnit v3** on **Microsoft.Testing.Platform** (opted in via `global.json`). Filters use
  `--filter-class` / `--filter-method`; coverage uses Microsoft's code coverage extension
  (`--coverage --coverage-output-format cobertura`).
- Every test project targets `net9.0` and `net10.0`: each test runs once per Jellyfin line.
- `Microsoft.Extensions.TimeProvider.Testing` (`FakeTimeProvider`) for time, NSubstitute only for Jellyfin interfaces.

## Test projects

| Project | Covers |
| --- | --- |
| `Core.Tests` | Codec, reply parser, client against the fake server, options validation, test pattern, player, tester, FFmpeg command lines and the frame source against a real FFmpeg, playback monitor, streaming session (fake time and frames), end-to-end streaming (real FFmpeg → fake server) and, in `EndToEnd/`, the client against a real Hyperion.ng and HyperHDR |
| `Tests` | Plugin wiring: ids and resources consistent across C#/HTML/JS/`plugin.json`, configuration XML compatibility, controller validation and behaviour, media source resolution |
| `TestSupport` | `FakeHyperionServer`, `RecordingSink`, `RecordingGrabSessionFactory`, `OfficialHyperionCodec`, `TestHelpers` (shared, not a test project) |

## The fake Hyperion server

`FakeHyperionServer.Start()` listens on `127.0.0.1` with an OS-assigned port and records every request:

```csharp
await using var server = FakeHyperionServer.Start();                 // or RegistrationMode.Reject / Silent
await using var client = await HyperionClient.ConnectAsync(new() { Host = server.Host, Port = server.Port }, logger, ct);
var register = await server.NextRequestAsync<RegisterRequest>();     // awaits, with a 5 s timeout
server.DropConnections();                                            // simulate a Hyperion restart
```

It decodes with the **official** FlatBuffers runtime and verifier, so a test that passes proves Hyperion would accept
the bytes. Do not change the fake server to make our encoder pass.

## FFmpeg tests

`FfmpegFrameSourceTests` run the real FFmpeg on a clip generated by `FfmpegFixture` (lavfi: one second each of red,
green, blue and white, 320x180 at 25 fps) and assert the colors at known positions, the frame timing, the buffer pool
throttling and that the process is killed.

- FFmpeg is taken from `HYPERION_GRABBER_FFMPEG` or the `PATH`; without it these tests are **skipped**.
- `HYPERION_GRABBER_REQUIRE_FFMPEG=true` makes a missing FFmpeg a failure. CI on Linux installs FFmpeg and sets it.
- `FfmpegToneMappingTests` decode a lossless 10-bit BT.2020 clip, tagged PQ and HLG, with exact code values (`geq`,
  FFV1): one second each of black, a gray at about 100 nits and a saturated orange. Untreated, the gray comes out at
  130 of 255 and the orange as a pale brown; tone mapped, black stays black, the gray is above 180 and the orange
  saturated. They run once per tone mapper (`tonemapx`, `zscale`) with the first FFmpeg that has it.
  `HYPERION_GRABBER_JELLYFIN_FFMPEG` names Jellyfin's FFmpeg, the only one with `tonemapx`; CI on Linux installs
  jellyfin-ffmpeg from Jellyfin's APT repository next to the system FFmpeg, sets it, and then requires both tone
  mappers to be tested.
- `StreamingIntegrationTests` use the same clip end to end: fake playback events go through `PlaybackMonitor` and a
  real `StreamingGrabSessionFactory` (FFmpeg reading `file:<clip>`, `HyperionClient`) to `FakeHyperionServer`, which
  must receive the frame at the playback position, frames in playback order and pace, and a `Clear` on stop.
- `StreamingGrabSessionTests` drive a session tick by tick with `FakeTimeProvider`, a `FakeFrameSource` (frame *n*
  carries *n* in its first byte) and a `RecordingConnection` that can hold or fail sends; they cover dropping,
  pause keep-alive, seeks, a lagging decoder, failures and the bounded dispose.
- Hardware decoding is only tested on request: set `HYPERION_GRABBER_HWACCEL` to `Nvenc`, `Qsv`, `Vaapi`, `Amf`,
  `VideoToolbox` or `Rkmpp` (and `HYPERION_GRABBER_HWDEVICE`, for example `/dev/dri/renderD128`, for VA-API / QSV on
  Linux) and run `dotnet test --solution Jellyfin.Plugin.HyperionGrabber.slnx -c Release -- --filter-method "*WithConfiguredHardware*"`.
  Jellyfin's own FFmpeg (`/usr/lib/jellyfin-ffmpeg/ffmpeg`) is the best choice for this. `*OnConfiguredHardware*`
  does the same for HDR: an HEVC Main 10 PQ clip (needs libx265) through the GPU scaler in `p010` and the tone mapper.

## End-to-end tests against Hyperion.ng and HyperHDR

`EndToEnd/HyperionEndToEndTests` run `HyperionClient` and `TestPatternPlayer` against a real Hyperion.ng or HyperHDR
and look inside it over its JSON-RPC API (TCP 19444): the priority list (`serverinfo`) and the colors each instance
computes for its LEDs.

| Test | Checks |
| --- | --- |
| `TestPattern_IsListedWithItsOriginWhilePlaying_AndClearedAfterwards` | While the pattern plays, priority 150 is listed as `FLATBUFSERVER`, origin `Grabber E2E@<address>`, active and visible; after the player's `Clear` it is gone while the connection is still open |
| `TestPattern_LightsTheLedOfEachEdgeInThatEdgesColor` | LEDs sampling the middle of the top, right, bottom and left edge show red, green, blue and yellow: byte order and orientation of our `RawImage` |
| `Picture_ReachesEveryRunningInstance_EachThroughItsOwnLayout` | With two running instances (the second samples the regions in reverse order) both show the picture through their own layout, and both list our origin |
| `Picture_ReachesAnInstanceStartedWhileStreaming` | An instance started while we stream shows the picture |
| `BlackBars_AreCutOffByHyperion_SoTheEdgeLedsShowThePicture` | A letterboxed (bars at the top and bottom) and a pillarboxed (bars at the sides) test pattern light every edge LED in the pattern's color, not black: Hyperion's black bar detector finds the bars in our picture ([ADR 0013](adr/0013-black-bars-and-aspect-ratio.md)) |
| `Picture_ComesBack_AfterTheRemoteControlClearsOurPriority` | After a JSON-RPC `clear` of priority 150 on instance 0 (as from the web UI's remote control), the next images over the same connection light the LEDs again: Hyperion.ng asks for a new `Register` with `registered = -1` and the client sends it; HyperHDR registers the priority itself on the next image |

Colors are compared by which channels are on, because Hyperion.ng's brightness compensation and smoothing change the
values (yellow arrives as `128,128,0`; HyperHDR reports the exact colors, before its color processing). Reads are
repeated until they match or 15 s pass (`Eventually`), since a server handles the FlatBuffers and JSON-RPC
connections independently.

The two servers share most of the JSON-RPC API. `HyperionServerApi` holds the common part (`HyperionJsonRpc` is only
the connection); `HyperionNgApi` and `HyperHdrApi` cover the differences:

| | Hyperion.ng 2.2 | HyperHDR 22 |
| --- | --- | --- |
| Instance of a request | `instance` field in the request | per connection: `instance` / `switchTo` (the schemas reject an `instance` field); every command fails with "Not ready" while that instance is stopped |
| LED colors | `instance-data` / `getLedSnapshot`: what goes to the device, after smoothing | `ledcolors` / `ledstream-start`: a stream of flat `[r, g, b, ...]` arrays, before smoothing |
| Settings | `config` / `getconfig`, `setconfig` for any instance, running or not | for the connection's running instance only; `setconfig` checks the full settings, so they are read, changed and written back. A new instance's `getconfig` came back without `foregroundEffect`; `setconfig` fills in defaults for what is missing |
| Factory password | `hyperion` | `hyperhdr` |

- **The servers.** `tests/e2e/hyperion-ng/Dockerfile` installs the `hyperion` package from Hyperion's official APT
  repository (Debian bookworm). That repository keeps only the current release, so CI always tests the version users
  install. `tests/e2e/hyperhdr/Dockerfile` installs HyperHDR's Debian bookworm package from its GitHub release, pinned
  by tag and SHA-256: HyperHDR's APT repository also keeps only the latest release, and the plugin documents support
  for HyperHDR 22. To test a newer HyperHDR, change the three `ARG`s (the digest is on the release page and in
  `gh api repos/awawa-dev/HyperHDR/releases/tags/<tag>`). The job summary names the version.
- **CI.** The `End-to-end (Hyperion.ng)` and `End-to-end (HyperHDR)` jobs (one matrix job) build and start a container,
  set `HYPERION_GRABBER_E2E_HOST=127.0.0.1` and run the `EndToEnd` namespace for both builds one after the other
  (`--max-parallel-test-modules 1`), because they share the server. The server's log is printed after the tests.
- **Skipped** everywhere else: without `HYPERION_GRABBER_E2E_HOST` the tests report as skipped.
- **Preparation.** `HyperionServerFixture` asks the server what it is (`sysinfo`), logs in with its factory password
  (override with `HYPERION_GRABBER_E2E_PASSWORD`), gives instance 0 four LEDs on the `file` device, creates the
  instance `Grabber E2E second instance` with the reverse layout, turns off the startup effect, turns on the black bar
  detector with Hyperion.ng's defaults (HyperHDR's default is off) and waits for the startup effects already playing. It refuses to run when any instance uses a device other than `file`, so it cannot overwrite a real
  setup. HyperHDR shows the settings of running instances only, so a stopped instance other than the fixture's own is
  refused too.

Run them locally with Docker (`hyperhdr` instead of `hyperion-ng` for HyperHDR):

```bash
docker build -t hyperion-ng-e2e tests/e2e/hyperion-ng
docker run -d --rm --name hyperion-ng-e2e -p 127.0.0.1:19400:19400 -p 127.0.0.1:19444:19444 hyperion-ng-e2e
HYPERION_GRABBER_E2E_HOST=127.0.0.1 dotnet test --project tests/Jellyfin.Plugin.HyperionGrabber.Core.Tests -c Release --max-parallel-test-modules 1 --filter-namespace "*.EndToEnd"
docker stop hyperion-ng-e2e
```

In PowerShell set the variable with `$env:HYPERION_GRABBER_E2E_HOST = '127.0.0.1'` first. Other ports:
`HYPERION_GRABBER_E2E_FLATBUFFERS_PORT` and `HYPERION_GRABBER_E2E_JSON_PORT`. Add `-p 127.0.0.1:8090:8090` to watch the
web UI while the tests run.

Not covered: real LED devices (the routing to instances does not depend on the device) and the servers' idle timeout
against the pause keep-alive.

## Kinds of tests and where they matter

| Kind | Example | Why |
| --- | --- | --- |
| Cross-implementation | encoder output decoded by Google.FlatBuffers | Our codec is hand-written |
| Golden bytes | `WriteClear_ProducesExactWireFormat` | Accidental layout changes are caught and must be justified |
| Robustness / fuzz | random and truncated replies | Network input is untrusted |
| Contract | test pattern colors and direction | Users follow the documented pattern |
| Consistency | GUID in C#, JS, `plugin.json` | Duplicated identifiers drift otherwise |
| Compatibility | old configuration XML still loads | Users' servers keep old files |
| Time-dependent | `PlayAsync_PacesFramesWithTheTimeProvider` | Deterministic, no wall-clock flakiness |

## Rules

- No fixed sleeps for synchronization (`TestHelpers.WaitUntilAsync`, awaitable fake server, `FakeTimeProvider`).
- Fixed seeds for random data.
- Network only on loopback with OS-assigned ports (the end-to-end tests use the container's mapped ports).
- Pass `TestContext.Current.CancellationToken`.
